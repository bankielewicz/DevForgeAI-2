## CS-6 The record's release is the executing release (finding 2, rule S06.9)

- **CS-6.1 Condition 9 is decidable only by the protected validator.** Installed mode is the validator running under a verified release root `R` (`RELEASE.sha256` above its own module, CS-2.2). A record with `trust_stage: PROTECTED_RELEASE`, `proven: PASS` or `closed: true` validated by a staged validator (no `R`) is rejected: "condition 9 is decidable only by the installed validator". Test: `test_closed_record_rejected_by_staged_validator`.
- **CS-6.2 Exact executable.** `protected_release.executable_path` must equal the string `<R>/bin/devforge` and `executable_sha256` its digest. A record naming another verified, root-owned release is rejected. Test: `test_record_release_differs_from_executing_root_rejected` (two protected roots, the record names the one that is not executing).
- **CS-6.3 Release identity file.** `<R>/RELEASE-IDENTITY.json` is listed in `RELEASE.sha256` and validates against `schemas/devforgeai/v1/release-identity.schema.json`: `identity_format: devforge-release-identity/v1`, `version`, `devforge_commit`, `devforge_tag`, `candidate_repository`, `candidate_checkpoint_id` (the checkpoint whose candidate the release was built from), `candidate_source_commit`, `candidate_manifest_sha256`, `schema_set_version`, `contract_policy_version`, `launcher_toolchain`, `built_at`. It never contains the digest of `RELEASE.sha256` (circular). Test: `test_release_identity_missing_rejected`.
- **CS-6.4 Binding.** For every closed record: `protected_release.version`, `source_commit`, `schema_set_version` and `contract_policy_version` equal the identity's `version`, `devforge_commit`, `schema_set_version` and `contract_policy_version`, and `contract_policy_sha256` equals the identity's `candidate_manifest_sha256` (the installed policy *is* the promoted candidate manifest). For the record named by `candidate_checkpoint_id`: `enforcement.candidate.source_commit` and `manifest_sha256` equal the identity's `candidate_source_commit` and `candidate_manifest_sha256`, so that record's pin can never move after promotion. Any inequality rejects. Tests: `test_release_identity_candidate_mismatch_rejected`, `test_release_identity_version_mismatch_rejected`, `test_release_identity_devforge_commit_mismatch_rejected`, `test_policy_not_candidate_manifest_rejected`.
- **CS-6.5** The promotion and permissions evidence files stay mandatory and digest-bound (CS-1.5) as human evidence; the identity file is the machine record the validator parses.

## CS-7 Git identity is not caller-controlled (finding 1)

- **CS-7.1 Sanitized Git subprocess.** Every Git call runs `/usr/bin/git` (absolute) with an explicit environment of exactly `PATH=/usr/bin:/bin`, `HOME=/nonexistent`, `LC_ALL=C`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`; nothing is inherited, so `GIT_DIR`, `GIT_WORK_TREE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_COUNT`/`GIT_CONFIG_*`, `GIT_EXTERNAL_DIFF`, `GIT_INDEX_FILE` and `GIT_CEILING_DIRECTORIES` have no effect. Only plumbing is used (`rev-parse`, `cat-file`, `merge-base`, `ls-tree`, `rev-list`, `diff-tree`). Tests: `test_git_environment_ignored` (one subtest per variable: the verdict equals the canonical one), `test_path_shadowed_git_ignored` (a `git` shadow first on `PATH` that exits 99 is never run).
- **CS-7.2 Remaining surface, stated.** Workspace-resident Git state (`.git/config`, `objects/info/alternates`, a linked worktree's `gitdir` pointer, the object store itself) is agent-writable and cannot be sanitized by the validator. It is defused, not removed, by CS-9 (the human fixes head and record digest in a root-owned attestation) and CS-6.4 (the release fixes the candidate commit): an attacker would need a second object with the same SHA-1. Recorded as a limitation on the record.
- **CS-7.3** The launcher's `env_clear` (CS-8.2) is a second layer; the validator never relies on it.

## CS-8 `bin/devforge` is a static Rust binary (finding 3)

- **CS-8.1 Static.** `bin/devforge` is an ELF executable for `x86_64-unknown-linux-musl` with no `PT_INTERP` program header and no `DT_NEEDED` entry, built from `components/devforge-release/launcher/` (Cargo package `devforge`, no dependencies: `Cargo.lock` lists one package). Tests *(component)*: `test_launcher_is_static`, `test_launcher_lock_has_no_dependencies`.
- **CS-8.2 Explicit environment.** The launcher calls `Command::env_clear()` and sets exactly `PATH=/usr/bin:/bin`, `LC_ALL=C.UTF-8`, `LANG=C.UTF-8`; the child sees nothing else. Test *(component)*: `test_launcher_child_environment_is_exact` (`LD_PRELOAD`, `LD_AUDIT`, `GIT_DIR`, `PYTHONPATH`, `PYTHONHOME` set in the parent; the child's environment equals the three variables).
- **CS-8.3 Loader variables are inert.** With a constructor shared object in `LD_PRELOAD` (and separately `LD_AUDIT`) the launcher runs and no constructor executes; the positive control (`/bin/sh -c true` under the same variable) shows the constructor does fire elsewhere. Tests *(component)*: `test_launcher_ignores_ld_preload`, `test_launcher_ignores_ld_audit`.
- **CS-8.4 Root from the running executable.** The release root is the parent of the directory of the resolved `/proc/self/exe`, which must be named `bin`; the launcher execs `/usr/bin/python3 -I -B -P <root>/bin/devforge-checkpoint.py` regardless of the working directory; a relative `argv[0]` is refused with exit 2. Tests *(component)*: `test_launcher_root_from_running_executable`, `test_launcher_refuses_relative_invocation`.
- **CS-8.5 Command surface.** `devforge checkpoint validate --plan <dir> [--diff <base>..<head>] [--json]` is passed through; `devforge checkpoint attest …` is CS-9.3; anything else exits 2 with usage. Test *(component)*: `test_launcher_refuses_unknown_command`.
- **CS-8.6 Pins.** `launcher/Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` (channel and the musl target), `src/*.rs`, `build.sh` and `BUILD-DIGEST.txt` (the `rustc -Vv` identity, the target, the build flags and the SHA-256 of the produced binary) are in the candidate manifest. DevForge rebuilds with the pinned toolchain and must reproduce the digest, or record the deviation and its cause in the promotion record. Test *(component)*: `test_build_digest_matches_binary`.

## CS-9 Closure range from a root-owned attestation (finding 4, rule S14)

- **CS-9.1 Format.** JSON, `attestation_format: devforge-closure-attestation/v1`, validating against `schemas/devforgeai/v1/closure-attestation.schema.json`: `repository_identity` (SHA-256 over the sorted root-commit SHAs joined by LF), `repository_root_commits`, `plan_path`, `plan_id`, `checkpoint_id`, `record_path`, `base_commit`, `head_commit`, `record_sha256` (the record blob at `head_commit`), `release_root`, `release_identity_sha256` (digest of `<R>/RELEASE-IDENTITY.json`), `authority_id`, `review_reference`, `minted_at`, `minted_by_uid`.
- **CS-9.2 Fixed location.** `/var/lib/devforge/attest/<repository_identity[:32]>/<plan_id>/<checkpoint_id>.json`. No option, environment variable or file selects another location; the in-process seam (`ReleaseFS.attest_root`) is the only override and the CLI cannot reach it. The file and every ancestor satisfy the protected path rule (CS-1.3). Test: `test_attestation_user_owned_rejected` (subprocess path).
- **CS-9.3 Minting.** Only `devforge checkpoint attest --repo <checkout> --plan <plan path> --checkpoint <id> --base <sha> --head <sha> --authority <id> --review <reference>` (the Rust binary) writes an attestation: it requires uid 0, resolves base and head through the sanitized `/usr/bin/git`, requires base to be a proper ancestor of head, reads the record blob at head for the digest, reads its own `RELEASE-IDENTITY.json`, refuses to overwrite an existing file (a new review replaces it by explicit removal), and writes with mode 0644 under 0755 directories. `--dry-run` prints the document and writes nothing. The document's digest is recorded in the PR review, never in the attested commit. Tests *(component)*: `test_attest_dry_run_validates_against_schema`, `test_attest_refuses_without_root`.
- **CS-9.4 Validation (S14).** For every closed record the validator reads the attestation at the fixed location and rejects unless all hold: protected path chain; parses and validates; `repository_identity` equals the identity computed from the plan's repository; `plan_path`, `plan_id` (README `| Plan ID |`), `checkpoint_id` and `record_path` match; `head_commit` resolves and is `HEAD` or an ancestor of `HEAD`; `base_commit` is a proper ancestor of `head_commit`; `record_sha256` equals the record blob at `head_commit` and the record on disk; `release_root` equals `R` and `release_identity_sha256` equals the digest of `<R>/RELEASE-IDENTITY.json`; `authority_id` equals the plan's decision authority; `minted_by_uid` is 0. Tests: `test_closed_record_without_attestation_rejected`, `test_attestation_head_not_ancestor_rejected`, `test_attestation_record_digest_mismatch_rejected`, `test_attestation_release_identity_mismatch_rejected`, `test_attestation_wrong_checkpoint_rejected`.
- **CS-9.5 Range.** S10 runs over `base_commit..head_commit` of the attestation, never over a caller range. `--diff`, when given, must resolve to exactly those two commits, else S14 rejects. `RangeRequired` and the CS-3.1 usage error are withdrawn: a closed record without `--diff` is validated through its attestation. Tests: `test_diff_differs_from_attested_range_rejected`, `test_closure_range_comes_from_attestation` (positive, no `--diff`), `test_post_closure_repin_rejected` (the reviewer's reproduction: implementation change and re-pin after the attested head, validated with the implementation commit as base).
- **CS-9.6 After the merge.** Once the closure PR merges with a merge commit, `HEAD` moves past `head_commit`; the attestation still holds because `head_commit` stays an ancestor, the record digest is unchanged and S13 requires the candidate bytes unchanged at `HEAD`. Test: `test_attestation_holds_after_later_commit` (positive).
- **CS-9.7 Path components are never agent-steered.** `plan_id` (read from the plan README at the attested head) and `checkpoint_id` must match `[A-Za-z0-9_][A-Za-z0-9._-]*`; the minter refuses otherwise (exit 1, nothing written) and the validator rejects (S14), so no agent-authored string can redirect the root-owned write or the lookup. Tests: `test_attest_refuses_hostile_plan_id` *(component)*, `test_attestation_hostile_plan_id_rejected`.
